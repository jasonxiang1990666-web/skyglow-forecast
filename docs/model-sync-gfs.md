# modelSync：上海 GFS / EC 数值同步

## 本阶段范围

`modelSync` 每 6 小时自动同步一次上海未来 48 小时的 GFS 与 EC 数值预报，并写入 `modelSnapshots`：

- `totalCloud`：总云量，0–100%。
- `lowCloud` / `midCloud` / `highCloud`：低、中、高云量，0–100%。
- `precipitation`：逐小时预报降水量，单位 mm。
- `humidity`：相对湿度，0–100%。EC 由 2 米气温与露点推导；GFS 直接读取。
- `visibility`：能见度，单位 km；上游默认以米返回，写入时已换算为 km。
- `source`：分别写为 `GFS` 与 `EC`，以便详情页独立比较。

本阶段不会改动霞况评分或“出现概率”；这些字段只用于详情页的模型一致性和数值解读。云图仍将在后续阶段接入。

## 数据来源与实现边界

云函数通过 Open-Meteo 的 GFS / ECMWF JSON 接口分别读取 NOAA GFS 与 ECMWF IFS 的公开数值字段。这样可以在现有 Node.js 云函数中稳定获得结构化数据；它**不是**直接下载并解析 NOAA NOMADS 或 ECMWF 的 GRIB2 原始文件。

后续若需要完全直连原始 GFS 文件，可将本函数中的 `buildProviderUrl` / `requestJson` 替换为独立的数据处理服务，再保持写入数据库的字段格式不变。

## 部署步骤

1. 在微信开发者工具中，右键 `cloudfunctions/modelSync`。
2. 选择“上传并部署：云端安装依赖”。
3. 部署完成后，云开发控制台会自动创建 `sync-gfs-shanghai` 定时触发器；它会在每天 04:30、10:30、16:30、22:30 运行，并同步 GFS 和 EC。
4. 首次验证可在云函数控制台测试，输入 `{ "source": "EC", "dryRun": true }`。成功后再以 `{ "source": "EC" }` 运行一次，写入正式 EC 记录。
5. 在 `modelSnapshots` 中确认生成的记录满足：`source: "EC"`、`city: "上海"`、`status: "ready"`，并含有总云量、分层云量、降水、湿度、能见度与 `validAt`。

不填写 `source` 或传入 `{ "source": "ALL" }` 时，会同时同步两套模式。`source` 也支持单独填写 `GFS`，用于单独排查某一套模式。

上海详情页会优先使用城市级 GFS 记录；仅在城市记录缺失时才回退至“全国”测试记录。

## 小程序读取逻辑

当前首页及霞况评分已改为实时模式：小程序打开时优先取得用户 GPS，经纬度随请求传入 `forecast`；云函数分别向 EC/GFS 数据接口请求当前位置的逐小时原始特征，并在下一次日出/日落目标时刻完成融合。首页评分不再读取本集合，也不再受“目标时刻前后 6 小时”快照窗口限制。GPS 授权失败时，才回退到用户手动选择城市的城市中心坐标。

`modelSnapshots` 仍保留给详情页的历史云图/模型参考卡片使用。用户进入朝霞、晚霞或火烧云详情页时，小程序会以该卡片的“建议观赏开始时间”为目标时刻，向 `forecast` 云函数请求模式参考；云函数按以下顺序选择快照：

1. 优先匹配同城市、同来源的记录，例如 `上海 + GFS`。
2. 该城市无数据时，才回退到 `全国 + GFS` 测试记录。
3. 在最新 100 条候选记录中，选择与目标时刻最接近的一条；相差超过 6 小时则显示“数据不足”。

详情页打开时会重新读取一次数据库；已经停留在详情页中的内容不会自动推送刷新，离开后重新进入即可获得下一轮同步后的数据。

## 可选环境变量

- `GFS_FORECAST_API_URL` / `GFS_FORECAST_API_KEY`：替换 GFS 数据服务地址或设置其 Key。
- `EC_FORECAST_API_URL` / `EC_FORECAST_API_KEY`：替换 EC 数据服务地址或设置其 Key。

默认地址无需在代码中填写密钥。若小程序进入商业化运营，请按数据服务商的授权与使用条款配置相应方案。
